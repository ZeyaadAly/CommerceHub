## Bounded API-01 handoff before implementation

Sources: API §§1.1/2/3/12/13/14 and API-001/033; architecture §§3/4/6/13/17; PRD NFR-API-01/NFR-SEC-05/06/NFR-TEST-01; legacy CH-P0-011 (module boundaries, validation, errors, OpenAPI, health); adopted CH-03/API depends only on accepted C. Existing health/smoke/environment tests are compatibility requirements.

- Approved versioned business transport prefix is `/api/v1`. Configure Nest URI versioning (`api` prefix, default URI version `1`); future routes use it. Keep existing GET `/health` outside prefix/versioning with its exact `{status:'ok'}` response. No new production endpoint or health alias is invented. Unknown routes/versions and unsupported methods retain the existing 404 status; no speculative 405/Allow contract.
- Use canonical shared Zod schemas through a global, typed Standard Schema-compatible adapter supported by Nest 12 metadata. Request arguments require an explicit schema; missing schema is a server contract error. Body/query/path validation returns schema output only (no arbitrary coercion), and strict input schemas reject unknown fields. Public details include only known top-level schema/decorator field names, capped at 16, with fixed validation codes; raw Zod messages/inputs/unknown keys are never copied.
- Generate server request IDs, ignore untrusted incoming ID values, and correlate fixed public error envelopes with minimal sanitized internal diagnostics. Reuse shared error/metadata contracts. No raw exception, SQL, request URL/query/header/body, arbitrary exception response or stack is returned/logged. Selected technical baseline status/code pairs are explicit in the implementation; unsupported/domain-specific exception mappings remain API-01 gaps rather than guessed business enums.
- Disable Nest default body parsing; register bounded strict JSON parsing only. `API_BODY_LIMIT_BYTES` is a technical startup budget (default existing framework-equivalent 100 KiB, accepted range 1–1 MiB); reject invalid configuration without values. This is an implementation safety ceiling, not final per-operation/rate/upload policy; production deployment limits still need OPS-01/SEC-01 review. No URL-encoded/multipart/compressed body support is enabled; body-bearing unsupported media returns 415. Unknown-route POST with no body remains 404. Use a simple query parser; repeated/compound values must pass their explicit schema.
- Preserve backend trust boundary. No CORS middleware, wildcard origin, cookies, session forwarding, authentication guard/bypass, CSRF negotiation or proxy trust selection. Production factory imports only AppModule/health and transport services; fixture controllers exist solely in test sources.
- Use supported pinned Nest Swagger tooling and Zod's public Standard JSON Schema conversion. Generate OpenAPI 3.1 locally/tests from actual routes, with canonical error/health schemas. Versioned paths are relative to `/api/v1`; legacy health overrides its operation server to `/`. Only `/health` is advertised by the production module. UI and raw-document HTTP routes remain unregistered in all environments; no unresolved public exposure policy is selected.

Technical recommendations above implement the explicitly authorized foundation, not a specialist sign-off. Material decisions still deferred: per-operation size/rate policies and upload/raw webhook handling, endpoint/domain status mappings and messages, API contract gaps BA-03/04/08/11–15, auth-cookie/CORS/CSRF origins, production Swagger access, all business schemas/financial limits and database/provider integration. Any new affected behavior needs its owning review. API-01 stays OPEN.

Primary tooling references checked before use: [Nest OpenAPI/Standard Schema](https://docs.nestjs.com/openapi/introduction), [Nest validation](https://docs.nestjs.com/application/validation). Installed Nest declarations and official npm metadata verify compatibility; no framework/pg upgrade is intended. Test runner remains the repository's existing node:test with local Supertest/Nest fixtures, avoiding an unrelated Jest/Vitest migration.

## Implementation, acceptance and results

The production factory configures the existing health-only AppModule. `common/http` owns correlation, bounded JSON parsing, versioning, explicit response projection and safe diagnostics; `common/pipes` owns schema validation; `common/filters` owns fixed error envelopes. Parser errors and out-of-prefix not-found responses enter the same boundary. No success interceptor changes legacy health or empty 204 responses. Unsupported methods remain 404. Future handlers must attach explicit shared schemas and public response projections.

The only additive shared exports are strict `healthResponseSchema` and its inferred type `HealthResponse`. Shared packages remain browser-safe and have no NestJS dependency. Existing pg, framework, Zod and frontend versions remain pinned. Added exact dependencies: Swagger 12.0.2; test-only Nest testing 12.1.3, Supertest 7.3.1 and Swagger Parser 13.1.0. The nonessential Scarf 1.4.0 install hook is explicitly denied through pnpm `allowBuilds`; esbuild's existing approval and supply-chain checks remain intact.

`pnpm --filter @commercehub/api openapi:generate` writes ignored `apps/api/dist/openapi.json` after build/init, without listening. Machine validation permits no external reference resolution. The production document is OpenAPI 3.1 with only GET `/health`, a root server override for health, canonical success/error schemas and no auth schemes. Test-only versioned routes prove body/query/path documentation and runtime validation; none are imported into production. No public Swagger UI or raw specification route is registered, including with a synthetic `SWAGGER_UI=true` environment.
